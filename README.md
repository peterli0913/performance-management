# TJ4 表格自动化工具集

凯莱英 TJ4 生产部表格处理工具。上传人员清单与安全质量奖核算数据，自动比出差异人员，
人工复核后生成**保留原格式与公式**的新核算表。目前覆盖核算文件的两张人员子表：

| 功能 | 生成哪张子表 | 取人口径 |
| --- | --- | --- |
| ① 一线人员 | `一线人员` | 清单「生产部」里职务为 助工/操作工/工程师/班长 的人 |
| ② 副主任&工艺组长及其他 | `副主任&工艺组长及其他` | 管理类职务（车间副主任/工艺组长/经理）+ 不在一线人员子表、且功能一也放不进一线车间的 助工/工程师/操作工/班长 |

两个功能共用上传、综合数据库和同一套复核/导出交互，但**复核状态各自独立**——
同一个人可能同时出现在两个功能里，决策不会串。顶部有功能切换。

## 快速开始

```bash
pip install -r requirements.txt
streamlit run app.py
```

首次打开会自动载入仓库里的两个示例文件，可以直接看到完整效果。

## 界面流程

| 步骤 | 说明 |
| --- | --- |
| 上传 | 多选文件，或把整个文件夹打成 `.zip` 上传（自动递归展开，支持 xlsx/xls/csv/docx/pdf） |
| 综合数据库 | 所有文件的所有子表合并进一个 SQLite：每个子表一张表，另有 `_files`/`_sheets`/`_documents`/`_problems` 元数据表，可写 SQL 交叉查询，也可下载 `.db` |
| 车间映射 | 「目前分组」到「车间」的对应关系，带置信度，可手工改，也可选择新建车间块 |
| 四类复核 | 每类一个页签，两种复核方式：「表格批量」勾选，或「逐条按钮」每人一组*应用修改*/*取消*按钮 |
| 生成核算表 | 两个导出按钮，见下 |

每个人有三种状态，两个勾选框是独立的，**文案直接写具体动作**而不是"应用/取消"：

| 分类 | 勾上的动作 | 不勾的动作 |
| --- | --- | --- |
| 新入职 / 待定·清单有核算无 | 新增到一线人员 | 不新增 |
| 离职人员 | 从一线人员删除 | 保留在一线人员 |
| 功能二的新增类 | 新增到副主任表 | 不新增 |
| 功能二的删除类 | 从副主任表删除 | 保留在副主任表 |

勾上 = 纳入「已应用版」；勾"不新增/保留" = 从**两个**导出里都剔除；两个都不勾 = 待定，只出现在「对照标记版」里。

## 判定规则

以人员清单「生产部」子表中**职务**为 助工（助理工程师）/操作工/工程师/班长 的人员为基准，
与核算数据「一线人员」子表按 **姓名 + 员工编号** 双匹配。参照日期默认从清单文件名解析
（`…，07-31-2026.xlsx` → `2026-07-31`），**新入职判定窗口日期**默认取参照日期前一个月。

| 分类 | 条件 | 导出时的动作 |
| --- | --- | --- |
| **新入职员工** | 清单有、核算无，且入职时间落在 **[窗口日期, 参照日期)** 之间；**或**出现在「人员变动说明」且离职时间为空 | 新增 |
| **待定·清单有核算无** | 清单有、核算无，但入职时间不在窗口内且变动说明里查不到 | 新增 |
| **离职人员** | 核算有、清单无，且在「离职人员&调出人员」子表；**或**在「人员变动说明」且有离职时间 | 删除 |
| **待定·核算有清单无** | 核算有、清单无，但查不到离职记录 | **自动按清单处理，见下** |

### 待定·核算有清单无：自动判定 + 逐人可改

示例文件里这 16 人全部能在「生产部」里找到本人——他们没离职，只是职务变了
（班长→车间副主任、助工→工艺组长、操作工→清洗工）或姓名录错。
所以这一类都按人员清单的信息处理，**动作由系统先判、每个人都能手工改**：

| 动作 | 含义 | 自动判定条件 | 示例文件人数 |
| --- | --- | --- | --- |
| **保留在一线人员** | 留在「一线人员」并按清单改写姓名/员工编号/职务/入职日期 | 清单职务仍是 助工/操作工/工程师/班长 | 1 |
| **移动到副主任表格** | 从「一线人员」移除，写进「副主任&工艺组长及其他」对应车间 | 清单职务不是这四种 | 15 |

这一类不用勾「应用/取消」——表格里的**动作**列选什么就执行什么，
也有「全部改为…」和「恢复自动判定」的批量按钮。

两张子表的车间叫法不一样（一线人员写 `11号楼D级车间`，那张表写 `11号楼车间D级区域`），
所以目标车间同样用两表已匹配的人反推；反推不到的（清洗组 / DCS / 外围罐区泵房）
沿用一线车间名，追加在那张表人员区最下方并给出提示。

### 实习生

实习生有两种写法，都会被识别：

| 写法 | 人数 | 是否受「纳入实习生」开关影响 |
| --- | --- | --- |
| 「职位」写实习生（「岗位」才是实际岗位，示例文件里全是操作工） | 43 | 受影响——按职位过滤会天然排除，开关打开后按岗位归入职务分组 |
| 「职位」「岗位」都写实际岗位，只有**备注**里写着「校招实习生」 | 4 | 不受影响——职位本来就是目标职务 |

侧边栏有一个**实习生判断日期**（默认取参照日期），它有两个作用：

1. **决定要不要加入表格**：只有**判断日期之前**入职的实习生才加进去；
   之后入职（或入职日期缺失）的实习生**不加入表格**，会在提示里报出人数。
2. **分类**：按它把纳入的实习生分成**入职超过 3 个月**和**入职不到 3 个月**两类，
   在复核表里单列一列。

导出时实习生的**姓名/员工编号/职务/入职日期四格都填黄色底纹，并且不叠红字**——
否则在已应用版里新增人员的红色字体会盖过黄底，看上去就成了"红色的"。

### 同一个人两个名字

清单叫「曹睿晟」、核算叫「曹静旺」，员工编号同为 `ALS14679`。这种情况会被识别成同一个人，
合并为「按清单更新姓名」，**不会**既新增一行又改一行。

每条结果都带**判定依据**（命中了哪个子表的第几行、比较了哪个日期），以及必要的**提示**：

- 已在「副主任&工艺组长及其他」子表（默认排除，避免一人两处）
- 仍在「生产部」但职务已不是目标职务（多为晋升，如班长→工艺组长）
- 员工编号相同但姓名不一致 / 姓名相同但编号不一致（数据质量问题，不当成"一增一减"）

示例文件的实际结果（默认设置，含实习生）：两表一致 616 人，新入职 249 人，待定·需新增 53 人，
离职 41 人，待定·需核实 16 人（1 人保留更新 + 15 人移到副主任表），已在其他子表 59 人；
关掉实习生开关则新入职为 213 人。实习生 46 人：入职超过 3 个月 1 人、不到 3 个月 45 人。

## 两种导出

新增人员按**职务**插到对应车间里该职务那一段的最下面——新增助工排在助工最后一个之后，
新增操作工排在操作工最后一个之后，而不是一律堆到车间块尾部。落点按以下优先级确定：

1. 该车间**已有**这个职务 → 插在该职务最下面。同一职务被别的职务隔成几段时
   （示例文件里 `11号楼D级车间` 的助工是 51 人 + 1 人两段），插到**人数最多**的那一段末尾。
2. 该车间**没有**这个职务 → 按**标准职务顺序**插在排在它前面的最后一个职务之后。
   标准顺序由各车间块的实际排列反推：一线人员是 工程师 → 班长 → 助工 → 操作工，
   副主任表是 副主任 → 车间副主任 → 工艺组长 → 经理 → 工程师 → 班长 → 助工 → 操作工。
   （例：清洗组原本只有班长和操作工，新增的助工会插在班长之后、操作工之前，
   而不是扔到车间块最末尾。）
3. 按顺序应排在本块最前面 → 块首。车间列不合并的副主任表可以插到块首之前；
   一线人员是合并的，插到上一块末尾会被上一块的合并区吞掉，所以退到块内第一行之后。
4. 连车间块都不存在 → 新建（一线人员建合并块 / 副主任表逐行写车间名）。

| 按钮 | 行为 |
| --- | --- |
| **对照标记版** | 全量对照。新增 → 姓名与员工编号填**绿色**；需删除或需移出 → **保留原行**填**红色**；按清单更新 → 就地改值、改动的单元格填**橙色**。被点「取消」的人不纳入 |
| **已应用版** | 只处理被点「应用」的人：删除类**直接删行**；新增类**直接插入对应位置**且内容用**红色字体**；更新类就地改成清单里的值 |

「待定·核算有清单无」这一类不受勾选影响，两版都会自动处理。

配色一览：绿底=新增、红底=删除或移出、橙底=按清单更新、黄底=实习生、红字=已应用版的新增行。

两者都保留原文件的**全部子表、字体、行高列宽、公式、自动筛选、条件格式**；
改动只发生在「一线人员」和「副主任&工艺组长及其他」两张子表的人员行，
打开后 Excel 会自动重算。

### 两个来自源文件的注意点

1. 源文件 `G342/H342/J342` 本来就是 `=SUMIF(...,#REF!,...)`（有人删过行）。新增人员**不会**继承这个坏公式，
   会改用同列的正常公式，并在导出摘要里提示你顺手修一下原表那一格。
2. 「用清单数据」会把清单里的职务原样写进「一线人员」的职务列，所以那一列可能出现
   `车间副主任`／`工艺组长`／`清洗工`／`经理` 这些原本不属于该列取值范围的值。
   这是"用清单数据"的字面含义；如果这些人应该挪到别的子表，请用「沿用核算数据」并手工处理。

## 为什么不用 openpyxl 存盘

示例核算文件里有 openpyxl 保存时会**丢弃**的部件：

- `xl/externalLinks/` —— 「副主任&工艺组长及其他」子表有 128 个 `VLOOKUP(…,[1]生产部!$C:$C,…)` 依赖它
- `xl/printerSettings/`、`xl/customProperty*.bin`、`xl/drawings/vmlDrawing*.vml`（批注框）

所以 `tj4tools/xlsx_surgery.py` 直接改写 OOXML 的 XML 部件，未修改的部件逐字节原样复制。
行号变化时会重映射：公式引用（跳过他表与外链引用）、合并单元格、条件格式 `sqref`、
`autoFilter`、`dimension`、`definedNames`（`_FilterDatabase` / `Print_Area`），
并把 675 处共享公式展开成普通公式。

区间终点用了单独的映射语义：车间块末尾追加人员时，块内区间（`COUNTIF($L$3:$AP$73,"a")`、
合并区 `A3:A73`）和跨全表区间（`SUM(F3:J675)`、打印区域）都要顺延，否则新人会落在统计范围外。

## 功能二：生成「副主任&工艺组长及其他」

目标人群两组：

| 组 | 口径 | 示例文件人数 |
| --- | --- | --- |
| 管理类职务 | 清单「职位」为 车间副主任 / 副主任 / 工艺组长 / 经理，**不看**是否在一线人员表 | 68 |
| 一线四职务的余量 | 清单「职位」为 助理工程师(助工) / 工程师 / 操作工 / 班长，且**不在**一线人员子表 | 见下 |

**「不在一线清单里」的口径是固定的：除了不在一线人员子表，还要求功能一也放不进一线车间。**
这样同一个人不会被同时放进两张子表。示例文件里组二是 82 人，目标合计 150 人，
相对本表现有的 128 人是新增 33、移除 11。

（如果只看"是否出现在一线人员子表"，组二会是 319 人、目标 387 人——那批人正是功能一要往
一线人员里新增的人，会造成重复放人，所以不采用。库里保留了这个口径参数供测试对比。）

严格口径留下的是本来就没有一线车间可去的人（生产技术转移组、安全组、在其他厂区/部门人员…），
这也解释了为什么这张表本来就有这些车间块。

职务和车间的写法都和清单不同，两套映射都由两表已匹配的人反推：

| 清单职位 | 本表职务 | 依据 |
| --- | --- | --- |
| 车间副主任 | 副主任 | 已匹配 25 人里 23 人这么写 |
| 助理工程师 | 助理工程师 | 31 人 |
| 工艺副主管 | 工艺组长 | 3 人 |
| 安全员 | 助工 | 2 人 |

车间同理：清单 `11号楼D级区域` → 本表 `11号楼车间D级区域`（一线人员写的是 `11号楼D级车间`）。

### 这张表的两个版式陷阱

1. **车间列不合并**（一线人员是纵向合并的），所以插入的行必须每行都写车间名，不建合并区。
2. **第 130 行之后混排着档位参照表**（`产能利用率`、`基础档位 A/B/C/D` 占着 A~D 列，
   被 L 列的 `HLOOKUP($A$143:$H$144,2)` 引用）。解析必须在第一个空姓名行停下，
   否则会把 `A`／`0.3` 当成车间；插行后那个绝对引用会跟着顺延。
3. 车间名 `生产技术转移组（多肽）` 用的是**全角括号**。匹配时做了 NFKC 归一化，
   但写回必须用单元格里的原始文本，否则 Excel 里会变成两个不同的车间、块被拆开。

## 测试

```bash
pip install pytest
python -m pytest tests/ -q
```

不需要起浏览器，也不需要人工看截图。测试全部使用仓库里的真实文件做黄金样本，包含：

- 规范化与日期解析边界
- 公式行号重映射（函数名不被误认为单元格、字符串字面量不被改写、他表/外链引用不动）
- 四类判定的守恒关系与已知个体的分类；实习生的两种识别方式与 3 个月分类；同编号异名合并
- 待定·核算有清单无 的保留/移动分流；副主任表只解析到真实人员区（第 130 行之后是混排的参照表）
- 跨子表移动：一线人员删行 + 副主任表插行、车间列逐行写入、`HLOOKUP($A$143:$H$144)` 跟着顺延
- 功能二：两种口径的人数、职务/车间写法映射、全角括号原样写回、车间块保持连续
- 两个功能的复核状态互不干扰
- 页面上不能出现被 Streamlit magic 误渲染的原始对象（AST 静态检查 + 渲染树扫描）
- 新增人员落在正确的职务段末尾、职务段数不因插入而增加
- 新增行不继承块级统计公式、不继承源文件里的 `#REF!`
- 已应用版的红色字体只改颜色不改字号字体、实习生的黄色底纹、更新写回清单值
- 导出后的结构体检：行号唯一升序、单元格引用与所在行一致、合并区不重叠、
  `count` 属性正确、`sharedStrings` 未被改动、`calcChain` 及其 Override/Relationship 都已移除、
  所有 XML 部件格式合法、除 `calcChain` 外没有丢失任何部件
- `AppTest` 端到端跑通整个界面并生成 Excel，包含两条回归：
  勾选「应用」后多次 rerun 决策不能丢；界面预览的人数必须等于生成结果里的人数

## 部署到 Streamlit Community Cloud

1. 推送本仓库到 GitHub。
2. 新建 App，主文件填 `app.py`，依赖用 `requirements.txt`。
3. 上传上限已在 `.streamlit/config.toml` 调到 500MB。

容器文件系统是易失的，所有中间结果都在内存 `BytesIO` / 内存 SQLite 里，不会往仓库写文件。
